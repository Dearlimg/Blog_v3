# Pi Agent 设计对照与本项目实现

本次参考 Pi 的 [Agent Core 说明](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)、
[循环实现](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts) 和
[队列包装层](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent.ts)。
将适合现有 Go 服务的机制实现于本地，继续使用原有模型、bbolt 存储、权限、审批及预算。

| 可借鉴机制 | 原有问题 | 本次增加 |
| --- | --- | --- |
| 回合循环与消息边界 | 生成、工具执行、结束判定混在一个循环内 | 拆分 `loop.go` 的请求准备与 `runTurn`，工具结果全部到齐后才进入下一轮 |
| 工具预检与结构化结果 | 所有工具统一解码为 Args，遗漏字段和其他工具的字段未严格校验 | `executor.go` 按每个工具的 Schema 校验，预检后调用 Hook，统一成功、失败、取消与待审批回执 |
| 并行工具与有序记录 | 独立搜索也要依次等待 | 只读工具白名单、服务级并发上限、完成事件即时发出、模型结果保持调用顺序 |
| Steering 与 Follow-up | 运行中只能等待或停止 | 持久化的补充指令及追问队列、一次投递一条、优先补充、待处理消息可移除 |
| 运行和回合生命周期 | 只显示模型及工具片段，缺少整体状态 | 运行与回合起止事件、当前阶段、回合数及待完成工具 ID |
| 请求边界转换 | 运行流程和模型上下文边界不够清楚 | 统一准备模型请求，复制工具调用记录；UI 事件继续留在事件流，审批回执仍进入模型上下文 |

## 执行规则

普通回合顺序为：选取一条补充指令 → 整理上下文 → 准备请求 → 模型响应 → 工具预检与执行
→ 按调用顺序加入结果 → 回合结束。模型无工具调用时，执行原有目标验收；通过后再选择下一条
补充或追问，若没有待处理输入则结束。验收失败继续原任务，追问等待。

并发仅用于声明为只读且没有依赖的整批调用；只要批中有一个串行工具，整批串行。
审批工具始终保留现有人工批准流程，MCP、工作流和团队工具没有加入并行白名单。
发生取消或参数错误时也产生工具结束事件；工具 panic 被转换为失败结果。
MCP 返回 `isError=true` 时按失败结果记录，保留原始内容供检查。

运行中的补充消息有请求 ID。接收消息、移除消息和消费消息均在数据库事务内执行。
最后一次消费队列与结束封口也在一个事务中完成，以避免“接口已接受，但任务刚好结束”的消息丢失。
终态或重启时仍待处理的消息仅保留记录，由用户决定是否重新发送。

## 实现位置

- `internal/agent/loop.go`：请求准备、回合边界、继续与停止判定。
- `internal/agent/executor.go`：工具 Schema 校验、预检、并行调度与回执。
- `internal/agent/control.go`：消息队列 API、幂等、移除及结束封口。
- `internal/agent/runtime.go`、`stream.go`：运行持久化、重启恢复、阶段更新及 SSE。
- `view/JS/agent.js`：补充/追问入口、队列状态和回合显示。

## 取舍

当前模型接口保持兼容 DeepSeek；已有 Subagent、Team、Workflow、长期记忆与独立目标验收继续工作。
本次没有加入动态模型切换、任意插件代码加载、自动重试已产生副作用的工具，或自动恢复中断调用。
Pi 的通用请求/回合扩展回调也未整套迁入；先把已有 Hook、权限和结果记录收敛到统一执行路径。

## 验证

Go 回归覆盖严格校验、并发限制、串行屏障、结果顺序、工具 panic、取消、补充优先级、
追问时机、队列幂等、结束竞争、重启保留、身份隔离和真实回执保护。
浏览器回归覆盖 SSE、历史、停止、重连、认证及运行中入队/移除。
测试使用假模型及本地 HTTP 服务，不调用真实 DeepSeek 或外部 MCP。
